### What would make the 7 sha-judgeable (the systemic fix)
Fold every transitively-included `_helper`'s SHA into the caller's `flow_sha`. Concretely:
`emit_result.py` (run side) and the disk-sha computation (`live_tally.disk_shas`,
`coverage.py`) must hash the flow file **plus its included helpers**, not just the flow file.
Then a helper fix bumps every caller's `flow_sha` and normal run-vs-disk comparison judges
them. The include graph is already discoverable (`audit_structure.py` walks runFlow→helper).
Until then the only authoritative off-device reads are `commands.json` in each flow's debug
dir (it inlines helpers) or run-date vs the helper-commit date. **This flow_sha change is the
single thing standing between these 7 and a suite whose green anyone can believe.**

### Shadow-column measurement (`transitive_sha`, computed ALONGSIDE — changes nothing)
`qa/lib/transitive_sha.py` (`--selftest` PASSES). It folds included helpers' bytes into the
hash, reusing audit_structure.py's runFlow rules (string + block `file:` forms), and is run
next to flow_sha so no verdict changes and no baseline is invalidated.
- **Impl validated:** the `flow_only` column it prints reproduces emit_result.py exactly
  (matches every ON-DISK sha, e.g. draft_lifecycle `7279a69379dc`).
- **Structural result (selftest-proven):** a fix inside a helper moves `transitive_sha` but
  NOT `flow_only`. So every one of the **9** flows verify_fixes marks "-" becomes judgeable
  under `transitive_sha`. After the 2 already `commands.json`-confirmed green + 1 confirmed
  off-device (savesCount), it specifically rescues the **7**. Gap shrinks 23 → 7.
- **Measured lower bound (git dates):** for **6 of 23**, an included helper's last commit is
  NEWER than the flow file's, so `flow_only` is *provably* blind to a helper change there:
  `edit_listing_remove_photo`, `edit_listing_reorder_photos`, `saved_listing_goes_sold`,
  `undo_mark_sold`, `listing_detail_saves_count` (5 of the "-" set) **+ `draft_lifecycle`**.
  (Proxy under-counts: a flow re-committed after its helper fix resets its own git-date above
  the helper's, hiding the staleness — true set is ≥ this 6, up to the 9.)
- **Bonus finding:** `draft_lifecycle` carries a REAL sha (verify_fixes treats it as
  judgeable), yet a helper it includes changed AFTER it — so its `flow_only` green is
  *secretly stale*: a past run's sha can match today's while the helper underneath has moved.
  `transitive_sha` flags it; `flow_only` gives false confidence. So the shadow column does not
  only rescue the "-" flows — it catches a sha'd flow whose green cannot be trusted.
- **The one-line switch (rig owner):** point emit_result.py + live_tally.disk_shas +
  coverage.py at `transitive_sha`, and have audit_structure import `_direct_includes` from this
  module (one walker, no divergence). Reversible; until then this column changes nothing.

### THE HEADLINE — can the greens be trusted? (whole-suite trust scan)
The point that decides adoption is not coverage ("7 rescued") but **trust**: does a green mean
anything when the sha behind it is blind to the helpers the flow runs?
- Whole-suite scan: **165** flows currently read green (latest result = pass at their current
  flow_only sha — the rig calls them green). For **149 of those 165 (~90%)** an included helper
  was committed AFTER the flow file, so flow_only sha never captured that helper change. **The
  rig cannot distinguish "still green" from "green recorded before a dependency moved under
  it."** `draft_lifecycle` is the concrete named instance inside the 23.
- **HONEST caveat (this is not 149 broken tests):** the 149 is dominated by SHARED-helper churn
  — most flows include common helpers (e.g. `login.yaml`), so one recent helper commit flags
  every caller that predates it. So 149 is the count of greens the sha *cannot vouch for*, and
  equivalently the SIZE of the one-time re-pin below — not 149 regressions. The 16 clean greens
  are flows committed after all their helpers.
- **What adoption does on the FIRST run (state plainly):** every baseline reads "changed" at
  once, because no run has recorded a `transitive_sha` yet — the first run under the new scheme
  **RE-PINS all baselines**. This is a **one-time re-pin, NOT a regression**: nobody should read
  the wall of "changed" as a break. After that first re-pin, a helper fix moves exactly the
  affected callers and a green means what it says.

### Steady-state cost of adopting transitive_sha (measured from git)
- **Fan-out is enormous.** The top helpers are included by nearly the whole suite:
  `open_bundle` 284/286, `skip_onboarding` 280, `goto_login` 275, `open_language_picker` 241,
  `await_language_restart`/`confirm_dialog`/`ensure_english` 240, `ensure_buyer_mode` 160,
  `login` 156. So ONE edit to any of them stales ~240–284 flows at once.
- **Frequency (last 2 months):** 82 helper commits; **51 touched a ≥50-fan-out helper**, across
  4 distinct weeks — but the churn is heavily FRONT-LOADED by rig construction (a dense cluster
  2026-08-22→27, plus the multimagics→api migration 09-01→05). The most recent, settled weeks
  show only a handful. So it is neither "twice, both login.yaml" nor a permanent "most weeks" —
  it is *heavy while the rig is being built, occasional once it settles.*
- **Recommendation (owner's call):** adopt `transitive_sha` for the trust gain, but pair it with
  a **semantic filter** so only a helper change that can affect a caller's assertions re-stales
  that caller. With ~280-flow fan-out, a byte-level "any change stales all callers" rule would,
  in any week that touches a wide helper (and history shows those recur), force a near-full-suite
  re-run off a comment or whitespace tweak. Minimum viable: hash the helper's SEMANTIC steps
  (strip comments/whitespace) so cosmetic edits stale no one. Stronger: re-stale a caller only
  when the helper change touches a step it depends on. Without a filter the steady-state tax is a
  full-suite run per wide-helper edit; with it, near zero.

### Minimum-viable semantic filter — BUILT, PROVEN, and MEASURED (it barely helps)
`semantic_sha` / `semantic_transitive_sha` in `transitive_sha.py` hash the PARSED yaml, so
comments/whitespace drop out. `--selftest` PROVES it: a comment/re-indent edit to the deep
helper moves no caller's `semantic_transitive_sha` (while the byte `transitive_sha` does), and
a real step change moves it. **But the measurement over the same 2 months shows it removes
almost nothing:**
- WITHOUT filter: **51** wide-helper commits → **11,108** flow-stale-events.
- WITH the semantic filter: **49** commits → **10,544**.
- Suppressed as purely cosmetic: **2 commits / 564 events (~5%)** — `8187d28` (skip_onboarding)
  and `f01c55c` (open_bundle). Everything else was a REAL step change to a wide helper.

**Corrected conclusion (I over-promised "near zero" above):** the minimum-viable filter is
correct and free, so ship it — but it does NOT make steady-state cheap, because wide-helper
churn is overwhelmingly real content, not cosmetics. The real lever is the STRONGER filter
(re-stale a caller only when the helper change touches a step that caller depends on) — a
design with tradeoffs, left to the owner and deliberately unbuilt. The other honest mitigation
is simply that the 51 is front-loaded by rig construction (Aug 22–27 + the api migration); a
settled rig edits wide helpers rarely, so the absolute stale-events fall on their own.
**Net:** adopt `transitive_sha` for the trust gain (decisive) + ship the cosmetic filter (free);
do not expect either to solve steady-state — that is the per-step-dependency filter's job, and
it is the owner's call.
